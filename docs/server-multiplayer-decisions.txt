MULTIPLAYER AND SERVER DIRECTION — recorded November 13, 2026

These are future design decisions discussed with Alain, not implemented features.

Current state
- The loader targets the client/menu, with activation and settings per local world.
- Remote joining is blocked with resident local mods or a partially failed load.
- Hosting through the client does not establish compatibility with guests.
- Dedicated servers need separate integration and headless configuration;
  feasibility and native integration points remain to be investigated.

Preferred architecture
- The server is authoritative for actions/settings affecting the shared world.
- Configuration belongs to the server world. Only the host/authorized admins
  may edit it; clients may inspect it.
- Check required mods and compatible versions at connection time, with clear
  incompatibility messages.
- Define whether each mod is required on server, client or both. Installing
  identical DLLs everywhere does not automatically synchronize actions.

CarryOn: start with chests and their contents
- The client requests pickup or placement; the server validates and commits it.
- Validate permissions, pickup/placement conditions and current chest state.
- Prevent two players from claiming the same chest simultaneously.
- Preserve contents without duplication or loss during transfers.
- Replicate state and visuals to relevant clients.
- Define and test disconnects, carrier death and server restarts.

Keep these constraints in the loader and CarryOn design. Do not claim multiplayer
support before investigating native mechanisms and testing a host, guests and
a dedicated server. This note does not start server implementation.
